## Prompt / conversation

### User
do you know what is the latest mcp release?

### Agent
Researched and found the latest MCP specification is revision **2026-07-28** (finalized July 28, 2026) — described as the largest revision since launch. Key changes: stateless protocol core (no `initialize` handshake, no session IDs), per-request `_meta.io.modelcontextprotocol/*` metadata, `server/discover` method, new `MCP-Protocol-Version` / `Mcp-Method` / `Mcp-Name` HTTP headers, and `resultType` on result objects.

### User
update this repo to support the latest mcp release. can you also make it backward compatible with the current mcp release too

### Agent
Explored the codebase and found that protocol-level handling is fully delegated to the `fastmcp`/`mcp` libraries — there is zero custom protocol code (no `initialize`, `Mcp-Session-Id`, `ServerCapabilities`, or protocol-version logic anywhere in the repo). The server uses six fastmcp APIs (`FastMCP()`, `@mcp.tool`, `@mcp.resource`, `mcp.http_app(path="/").lifespan`, `combine_lifespans`, `mcp.run(transport="stdio", show_banner=False)`).

Researched the SDK landscape and found a hard constraint: supporting 2026-07-28 requires `mcp>=2.0.0`, but `fastmcp` (latest stable 3.4.6) pins `mcp<2.0`. The version that adds dual-era support (`fastmcp` 4.x) is referenced in changelog/docs but **does not exist on PyPI** — not even as a beta. So a true native dual-era upgrade is blocked on an unreleased dependency.

Designed and got approval for a plan that: (1) bumps to latest stable SDK (fastmcp 3.2.4→3.4.6, mcp 1.27.0→1.29.0), (2) adds a forward-compat module documenting the 2026-07-28 era and exact upgrade path, (3) surfaces the active protocol version in `get_config` / `/api/config`, (4) documents the gap honestly. Explicitly chose NOT to hand-roll a custom protocol-compat middleware on top of fastmcp 3.x, because the library owns JSON-RPC dispatch and a middleware rewriting `_meta`/headers would conflict with its internal handling.

## Files changed
- `pyproject.toml` — bumped `fastmcp>=3.0.0` → `>=3.4.6`; added explicit `mcp>=1.29.0,<2.0` (upper bound recommended by the MCP SDK for projects not yet on 2.x)
- `uv.lock` — regenerated (fastmcp 3.2.4→3.4.6, mcp 1.27.0→1.29.0, +transitive updates)
- `backend/mcp_compat.py` — **new** forward-compat module; single source of truth for protocol-era status (`ACTIVE_PROTOCOL_VERSION`, `SUPPORTED_PROTOCOL_VERSIONS`, `PENDING_PROTOCOL_VERSIONS`, `protocol_info()`); documents the 2026-07-28 spec changes and the fastmcp 4.x upgrade trigger
- `backend/mcp_tools.py` — import `protocol_info`; add `protocol` key to the `get_config` MCP tool
- `backend/api/reviews.py` — import `protocol_info`; add `protocol` key to the REST `GET /api/config` endpoint
- `backend/local_url_guard.py` — **new** SSRF guard for local-only HTTP egress; validates that server URLs resolve to loopback/private addresses before connecting, blocking public IPs, cloud-metadata (`169.254.169.254`), and non-http(s) schemes; provides `local_request()` (http.client-based) as the single egress point
- `backend/cli_client.py` — route `_probe_url` and `_api` through `local_request` instead of raw `urllib.request.urlopen`; removed now-unused `urllib.error`/`urllib.request` imports
- `scripts/capture_screenshot.py` — same `local_request` refactor for `_is_server_running` and `_api`
- `README.md` — new "Protocol compatibility" subsection under MCP Tools explaining current era, the 2026-07-28 target, and the fastmcp 4.x dependency constraint
- `AGENTS.md` — new "Protocol compatibility" section recording the era and instructing future agents not to hand-roll a compat layer

The SSRF hardening was prompted by the Mimosa pre-commit security hook, which flagged pre-existing `urllib.request.urlopen(variable)` call sites as CWE-918. The scanner is pattern-based (no inter-procedural taint tracking), so it could not recognize a guard placed before a raw `urlopen` call — the fix was to route all egress through a single `local_request()` helper built on `http.client`, eliminating the `urlopen` sink pattern entirely. Post-fix Mimosa scan: 0 findings.
